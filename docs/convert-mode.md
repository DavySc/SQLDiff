# Convert mode (P0)

`sqldiff-gui convert [FILE]` opens a two-pane page: T-SQL you can edit on the left, PostgreSQL on the right. The right side is regenerated about 150 ms after you stop typing (debounced; stale responses are dropped). A sample is shown when no file is given; nothing is ever written to disk. `--stdout` prints the conversion and the per-statement badges instead of serving the page.

T-SQL → PostgreSQL and T-SQL → Db2 for i have rules (`--to db2i`; see [Db2 for i](#db2-for-i) below). The feasibility study that led here is the "Live conversion feasibility" doc in the project; this is its phase P0.

## What "correct" means here

Every converted unit (a statement, a compound header such as `IF … THEN`, a routine header, or a hoisted `DECLARE`) carries a status, best to worst:

| Status | Meaning |
|---|---|
| converted | Rules that need no assumption, and the engine compared this unit with its input and found nothing |
| under assumptions | Equal if every listed assumption holds (each has a stable id such as `ASM-CI-COLLATION`) |
| needs a decision | Several faithful targets exist; the note says which one was emitted and the alternative |
| not proven | The engine's diff of input against output could neither show this unit equivalent nor find a difference (for example `equiv.unproven`, or transaction behaviour it could not prove), or did not compare it at all (`equiv.not-compared`); its rules' claim is unconfirmed, so it needs a check by hand |
| differs | The engine's diff of input against output found a difference, leftover T-SQL, or the output does not parse as PostgreSQL |
| not converted | No rule applies; the original is kept as a commented block with the reason |

The status is the worst of the rule notes and of the engine's own checks (`checked`): the diff of input against output, and the output checked on its own as the target dialect (`output_check`, what `sqldiff check -d <target>` reports). Any binding finding (unknown built-in, table, column, variable, type, routine signature), leftover source syntax (residue), target limit or hazard in the output makes its unit `differs`, proven or not; analysis findings about the code's own quality do not. A finding of the input-against-output diff whose verdict is `unknown` makes its unit `not proven` (`unproven` in the JSON), never `differs`: the engine found no difference, but it could not confirm the rules either. The ones that do not count are the same one-sided kinds: analysis hits, lints and hazards, and the binding, residue and limit findings that the output's own check decides (`sqldiff_convert::undecided`). A gating finding that points into no unit is listed in `unplaced`, and a file with one never counts as converted. The engine check runs the normal `sqldiff diff` of the input (side A) against the output (side B) and attaches each finding to the unit it points into, so engine findings such as `error.contract` or `write.unpaired` show up next to the statement that caused them. Today the cross-dialect engine cannot prove statement equality, so the best a unit can get is "converted": tested rules, no assumption, nothing found. "Proven" needs the equivalence and IR work.

A statement the engine never compared never counts as converted. Every reason the diff gives for not comparing something (`report.unknown_reasons`: a DDL statement it does not model, a call, a statement with no counterpart, a CATCH block, several routines in one file, …) names a line, and the innermost unit whose input or output holds that line becomes not proven with the note `equiv.not-compared` ("The engine did not compare this with its conversion: …"). A reason that names no line inside a unit (two routines of different kinds, different parameter counts) is listed in the file's `unproven` and keeps the whole file from counting as converted, like `unplaced`; the queue lists it in tier 2 and the gate blocks on it. What the engine compares is listed in `docs/cross-dialect-proofs.md`; `CREATE TABLE` between T-SQL and PostgreSQL is one of them ("Tables").

A rule never guesses: if any part of a statement has no rule (for example `@@ERROR`, `UPDATE … FROM` with a join, `DATEDIFF(week, …)`), the whole statement is commented out and marked not converted.

### Idiom rules

Before a statement is commented out, it goes to the idiom rules (`sqldiff_core::rules`, see [idiom-rules.md](idiom-rules.md)), which recognise whole patterns rather than tokens: `MERGE` and `IF EXISTS` upserts → `INSERT … ON CONFLICT`, `IF NOT EXISTS … INSERT` → `ON CONFLICT DO NOTHING`, the `LEFT JOIN … IS NULL` delete → `NOT EXISTS`, `INSERT` + `SCOPE_IDENTITY()` → `RETURNING … INTO` or `lastval()`, and `sp_getapplock` with its return-code check → `pg_advisory_xact_lock`. Their output replaces the comment when they convert the statement completely, with their notes (and an `idiom-rules` note naming the rules) on the unit. Patterns that span statements (`INSERT` + `SCOPE_IDENTITY`, `sp_getapplock` + its check) become one unit, since the token rules cannot see them as a pair.

Two limits keep this honest. Statements the token rules already convert keep their conversion (a plain `IF EXISTS … UPDATE … ELSE INSERT` stays an `IF`, with the race intact, rather than becoming an atomic `ON CONFLICT`). And a statement refused because of where it stands (a result set in a procedure, `COMMIT` inside a TRY block) is never handed to the rules, which see statements out of context. The rules never check themselves: their output goes through the same engine diff as everything else.

### Never silent

- A T-SQL built-in the target does not have (on the built-in lists in `profiles/builtins.toml`) refuses its statement instead of passing through: `HASHBYTES`, `CHECKSUM`, `SERVERPROPERTY`, `RAND(seed)`, … Names in object position (`INSERT INTO log (…)`) are not calls.
- Dynamic SQL whose text the code alone fixes (literals, `NCHAR`, `QUOTENAME` and `+` over them, and variables last set to such text; see [cross-dialect-proofs.md](cross-dialect-proofs.md#dynamic-sql)) is converted by the same rules and run as `EXECUTE '<converted statement>'` (PostgreSQL; Db2 for i not yet). `sp_executesql` with parameters becomes `EXECUTE '<converted statement with $1, $2, …>' USING …` when each value is a variable declared with exactly the parameter's type (otherwise T-SQL converts the value as it passes it, and PostgreSQL does not). The variable keeps its T-SQL text, which nothing runs any more, and the engine compares the statement inside the string with the one inside the `EXECUTE`. The rules' notes on the statement inside start with "In the dynamic SQL:". Text from a parameter, a table, a loop or anything else the reading does not follow is `not converted` with the reason, and so is known text that would run differently (a query, a `#temp` table, several statements, the caller's variables).
- The statements inside an IF, a loop or a CATCH block that the statement-level comparison does not cover are each `not proven` on their own line, like the IF itself: none counts as compared because its enclosing statement was reported elsewhere.
- A statement that builds text which another statement runs as dynamic SQL without that conversion is `differs` (`dynamic-sql.text`): the statement converts, the SQL in the string is still T-SQL.
- Inside a routine or block, a statement kept as a comment is followed by `RAISE EXCEPTION 'sqldiff: statement at source line N was not converted'` (Db2 for i: `SIGNAL SQLSTATE '75001'`), so the converted routine stops there instead of quietly skipping it. At the top level of a script the statement is only commented out.
- `WITH (…)` options are dropped only when they change storage or performance, never results (`DATA_COMPRESSION`, `FILLFACTOR`, `PAD_INDEX`, `ALLOW_ROW_LOCKS`, `IGNORE_DUP_KEY = OFF`, …). `MEMORY_OPTIMIZED = ON` with durable rows (no `DURABILITY`, or `SCHEMA_AND_DATA`) becomes a plain table under `ASM-MEMORY-OPTIMIZED` (SQL Server's optimistic concurrency errors and the statements it refuses on such tables are not reproduced); `DURABILITY = SCHEMA_ONLY` (no rows survive a restart), a memory-optimized system-versioned table, `IGNORE_DUP_KEY = ON` and anything unknown refuse the statement. An index declared inside CREATE TABLE (`INDEX ix [UNIQUE] [NONCLUSTERED] (cols)`) becomes a CREATE INDEX after the table, converted as one (columnstore and `HASH` indexes stay refused). A computed column becomes a `STORED` generated column on PostgreSQL only when its value and type are exact: a CASE over the row's columns tested with `IS [NOT] NULL`, `AND`, `OR`, `NOT`, whose results are bit constants (`CONVERT(bit, 0)`); a non-persisted column gives the same values because such an expression is deterministic (`ASM-COMPUTED-STORED`: an INSERT without a column list skips the column in T-SQL only, and PostgreSQL accepts `DEFAULT` for it). Other computed columns (string functions, JSON, arithmetic) stay refused, and Db2 for i has none. A `GEOGRAPHY` column becomes PostGIS `geography` on PostgreSQL (no type modifier, so each value keeps its own SRID as in SQL Server) under `ASM-POSTGIS-GEOGRAPHY`: the postgis extension is installed, and the output check takes the type under the same assumption. Values are carried as they are; spatial methods (`geography::Point`, `STDistance`, …) have no rule and stay refused. Db2 for i keeps refusing GEOGRAPHY, and `GEOMETRY` stays refused on both. `SYSTEM_VERSIONING = ON` has its own rule (below) for PostgreSQL and is refused for Db2 for i.

## Whole trees: `sqldiff convert`

```sh
sqldiff convert SRC -o OUT --to postgres   # or --to db2i; --from tsql is the default
```

`SRC` is a directory (every `.sql` file below it, hidden directories skipped) or one file. `OUT` mirrors the layout with the same file names, so `sqldiff tree SRC OUT --dialect-a tsql --dialect-b postgres` pairs them again. `OUT` must be empty (or pass `--overwrite`) and may not be inside `SRC`. Files are read as UTF-8 (with or without BOM) or UTF-16 with a BOM, as SSDT saves some; anything else is listed as unreadable and not converted. The pack's `[[helpers]]` reach the output's check: a call to a function a helper declares for the target dialect resolves, and is not reported as a routine missing from the catalog.

Two passes, each over `-j N` threads (default: all cores):

1. **Rules.** Every file is converted with the source catalog of the whole tree (`CREATE TABLE/VIEW/PROCEDURE/FUNCTION` from every input file). Rules that need another file use it: `EXEC p … @x OUTPUT` converts to `CALL p(…, v_x)` only when `p` is in the tree, every OUTPUT parameter of `p` gets a declared variable marked OUTPUT, and nothing else is marked OUTPUT (a CALL would assign an INOUT argument back where T-SQL does not). Named arguments then need no `ASM-PARAM-NAMES` assumption.
2. **Check.** Every file is diffed against its output and its output checked on its own, with the source catalog for side A and the catalog of the whole output tree for side B. A call, column or table defined in another file binds; one whose definition could not be converted does not exist in the output tree, so the statements that use it are `differs` (for example every query on a table whose CREATE TABLE was refused), except for the stand-ins below.

**Stand-ins for refused tables.** A CREATE TABLE refused only for computed columns, for `MEMORY_OPTIMIZED` / `DURABILITY` table options (`DURABILITY = SCHEMA_ONLY`, a memory-optimized system-versioned table) or, failing that, also for table-level CHECK constraints and non-unique inline indexes (which the catalog does not hold anyway), is converted again by the same rules without those parts (and, for a system-versioned table, with the left-out columns gone from its history table too). If that converts, the result stands in side B's catalog for binding only, its left-out columns present with no type, and the tree's own statements on it (indexes, keys) put on it. Nothing of it is written: the refused statement stays `not converted` as before, so its file never counts. Every unit that names the table (in the source, or in the output: `sp_addextendedproperty` names it in a string, its COMMENT ON by name), one of its indexes, or a view of the tree over it carries **`ASM-TABLE-STAND-IN`**, whose note gives the table's file and line, why it was refused and what was left out; it holds once the target table is created with the stand-in's columns and types, and goes away when that CREATE TABLE is written by hand into the review ledger. A unit that may touch a left-out column (its name, a `*` other than `COUNT(*)`, an INSERT into the table without a column list, a view over it that shows one) is **not proven** (`tree.refused-column`). Names are matched by text: a false alarm, never a miss; names inside dynamic SQL strings are not seen. A table refused for anything else (a type with no rule, a collation to choose) has no stand-in. Template trees do not use stand-ins yet.

Every unit that is not plainly converted gets a comment line above it in the output, `-- [sqldiff: under assumptions] ASM-…` or `-- [sqldiff: differs] bind.unknown-builtin` (not-converted units already open with `-- [not converted]`), so a reviewer reading only the output tree sees them. `--no-catalog` checks each file alone.

`OUT/conversion-report.json` has, per file, its status (the worst unit status), unit counts, time, and every unit that is not plainly converted with its input and output line (in the annotated file), rules and reason; totals by status and the most frequent blockers. `OUT/conversion-report.md` is the same for reading. Exit code 0 when every file is converted or converted under assumptions, 1 otherwise, 2 on usage or I/O errors.

The MCP server runs the same engine (`sqldiff_convert::tree`): `convert_tree` takes the same options and, given `out`, writes the same tree and reports; without `out` it writes nothing and `converted_file` returns one file's annotated output. `convert` converts one file or inline text as a tree of one. Statuses, rules and reasons are those of the report; only the output directory named in a binding reason differs when nothing is written (`SRC (converted, not written)`).

On WideWorldImporters (336 files, 58,610 lines, 4 cores): PostgreSQL in 9 s, Db2 for i in 25 s. 33 files convert completely for each target; most of the rest carry assumptions, dynamic SQL or tables that need types without a rule, whose dependants then do not bind.

### Mass conversion in the GUI

The Runs page's *Mass conversion* tab converts several source trees into several target dialects as one batch. Each source and target is an ordinary conversion run (what `sqldiff convert` runs) into `OUT/<source folder name>/<target>`, with its own review, done gate and run sheet; the runs go one after another, and a source is not converted into its own dialect. Every run is checked before any starts (paths, rules for the pair, packs, output folders that are not empty without *Replace files*, two sources with one folder name, a run writing where another reads or a running run writes), and the batch starts all or none. The summary matrix shows, per source and target, that run's own totals and done gate (`sqldiff review-status`), never a count made up for the batch. *Cancel all* stops every run that has not finished: queued runs never start, and a running one stops before writing. The batch's sheet is a script (sh or PowerShell) of its runs' commands in the same order, exiting with the worst of their exit codes; `crates/sqldiff-cli/tests/gui_parity.rs` runs it through the shell and compares the trees with the batch's.

### Base catalogs

```sh
sqldiff convert upgrade/ -o out/ --to postgres --catalog install/tables.sql --catalog install/procs.sql
```

A tree is often not the whole database: an upgrade script set alters and queries tables that an earlier install created. Without those, every statement that touches them is `differs` (`bind.unknown-table`, `bind.unknown-routine`). `--catalog FILE` (repeatable) gives a conversion **base catalogs**: DDL in the source dialect (`--from`) of objects that exist already but are not part of the tree.

- **What is read.** What the catalogs read from any DDL: `CREATE TABLE`, `CREATE VIEW`, `CREATE PROCEDURE`, `CREATE FUNCTION`, and `ALTER TABLE … ADD/DROP COLUMN`, `CREATE INDEX` and `CREATE SCHEMA` on them. Everything else in the file is ignored, not an error. A file is read as UTF-8 or UTF-16 with a BOM, as tree files are. Snapshot bundles (`.json`) are refused here: give DDL. Files fold in the order given; a later file's table replaces an earlier one's of the same name, and a later file's routine one of the same name and parameter count.
- **Side A (the source catalog)** holds the base objects, then the tree's own. **The tree wins**: an object the tree defines replaces every base object of that name (both tables and routines; for a routine, every overload, since a T-SQL procedure is replaced, not overloaded), with T-SQL's default schema read in (`orders` and `dbo.orders` are one name). A statement in the tree that alters a base table (`ALTER TABLE orders ADD …`) changes it. The rules see the base routines too: `EXEC next_line @order_id, @line OUTPUT` converts to `CALL next_line(p_order_id, v_line)` when `next_line` is only in a catalog file.
- **Side B (the target catalog)** holds the base objects **as the same rules convert them**, then the tree's converted files (the tree wins here too). The base DDL is converted with the base catalogs alone, never with the tree, one top-level statement at a time, and each statement is checked as a tree file is (diffed against its conversion, and the conversion checked on its own against the base catalogs), so every object gets its own verdict. It is not annotated, not written into `OUT`, and not counted in the report's files, units or statuses.
- **A base object whose conversion is not plain is suspect**: one whose statement is worse than converted under assumptions (a decision, not proven, `differs` or `not converted`: a refused `geography` column; a `datetime2` column, whose seventh fraction digit PostgreSQL does not keep), or one that a statement altering it or putting an index or trigger on it leaves so. An object whose statement uses a suspect object is suspect too (a view over it, in any catalog file or in the tree), until nothing more changes. Suspect objects **stay on side B** as converted; one the rules wrote no definition for (its statement kept as a comment) stands in as its source definition. Every unit in the tree that names a suspect object carries the assumption **`ASM-BASE-SUSPECT`**, whose note names the object, its file and line and its status; it is reviewed and accepted like any assumption, so the done gate blocks until a person has checked it. Names are matched by text: a column or alias named like a suspect object flags too (a false alarm, never a miss); names inside dynamic SQL strings are not seen. An object the tree defines replaces a base object of that name, so the base object's suspicion does not reach what uses the tree's. Base objects converted under assumptions are not suspect: their notes are listed in the report and not carried to the statements that use them, just as for an object another tree file defines.
- **The report** (`conversion-report.json` and `.md`) lists every base catalog file with its SHA-256 (CRLF read as LF) and how many tables and routines it defines (`base_catalogs`), one hash over their contents (`base_hash`), the suspect base objects with the reason (`base_objects` with `suspect: true`), those converted under assumptions (`suspect: false`), and base statements that define nothing and did not convert (`base_statements`). The binding reasons name the catalogs (`… does not exist in the PostgreSQL catalog (OUT and base catalogs install/tables.sql)`).
- **The target's own base DDL** (`--catalog-b FILE`, repeatable, in the target dialect) replaces the converted base on side B when it is at hand, such as the install as it really is on the target. Side B then binds against exactly those files as given: nothing is converted or flagged, and a base object they lack does not bind on side B (`differs`). It needs `--catalog` (side A needs the base objects too); the report lists its files as `base_catalogs_b`, and `base_hash` covers both lists.
- **Review decisions** made on a conversion with base catalogs record `base_hash`, and apply only while the conversion binds against the same contents: other contents, other files or none outdate them (`sqldiff review-status` lists them as `outdated`). Give `sqldiff review-status` and `sqldiff-gui review` the same `--catalog` and `--catalog-b` files, in the same order, as `sqldiff convert`; the GUI's review converts again when a catalog file changes.
- **`--no-catalog` and `--catalog` or `--catalog-b`** do not go together and are refused: `--no-catalog` checks each file alone, without any catalog.
- **Templates** (`--template`) take `--catalog` too. Catalog files are plain DDL: no placeholders are read in them.

The GUI's Runs page has the same fields (Base catalogs and Target catalogs, one file per line), and its run sheet lists every `--catalog` and `--catalog-b`; the MCP tools `convert_tree`, `conversion_queue` and `write_unit` take `catalogs` and `catalogs_b`.

## Templates

`sqldiff-gui convert FILE --template --pack PACK` converts a generator template. The placeholders and special forms follow the pack's `[template]` syntax and the same placeholder rules as `sqldiff diff --template` ([templates-and-composition.md](templates-and-composition.md)); `--parameter NAME` (repeatable) lists the parameter names when the delimiters could also be SQL (`[...]` in T-SQL), so only those names are placeholders.

The template's fragment (placeholders as `TPL_<NAME>` identifiers, special forms as comments) is converted and checked like any input, then the placeholders and special forms go back into the output as the template writes them, so the right pane is a PostgreSQL template for the same generator. Badges and spans point into the template. Each unit with a placeholder carries `ASM-TEMPLATE-PLACEHOLDER`: the placeholder was converted as a name, so every value the generator fills in must be a name PostgreSQL accepts there. A placeholder the rules renamed beyond recognition is flagged on its unit (`template.placeholder-lost`, differs), and a directive that did not survive in order is flagged too; neither is put back by guess. The header shows how many placeholders the template has.

```sh
sqldiff-gui convert docs/examples/templates/save-entity.tpl.sql --template --pack docs/examples/pack --isolated
```

A template with generator directives (special forms such as an include) has them converted as comments, without the text they add, and the text they add can change what the rest means (a header's `SET XACT_ABORT ON`, a declaration, the end of a block). So every unit of such a template carries `ASM-TEMPLATE-DIRECTIVE`: it holds only if the woven output does, and no unit of it counts as converted until the woven instances are checked.

### Template trees

```sh
sqldiff convert templates/ -o out/ --to postgres --template --pack PACK [--parameter NAME …] [--extension tpl …]
```

`sqldiff convert --template` converts a whole tree of templates the same way, with the same two passes, catalogs and report as plain files. The output tree holds templates for the target. Every file is read as a template; files without placeholders (an included header, say) come through as plain SQL. `--extension` (repeatable, default `sql`) picks the files when the generator uses another extension.

- **One set of stand-ins for the tree.** All fragments use the same stand-in name for the same placeholder, so a table that `tables/entity.tpl.sql` creates as `<%SCHEMA%>.<%TABLE%>` binds in every template that uses `<%SCHEMA%>.<%TABLE%>`, and a misspelt column there is `bind.unknown-column`.
- **The premise is stated.** Binding across templates assumes one weave fills each placeholder with the same value in every template; two templates woven with different values would bind to the wrong instance's object. So in a tree with catalogs every unit with a placeholder also carries `ASM-TEMPLATE-SHARED-VALUES`, discharged only by checking the woven instances (`sqldiff instances`). `--no-catalog` binds nothing across files and needs no such assumption.
- **No binding by guess.** An object whose name holds a placeholder and that more than one file creates (two templates both creating `<%SCHEMA%>.<%TABLE%>`, for different instances) is left out of the catalogs, so nothing binds against the wrong one; the units that use it still carry `ASM-TEMPLATE-PLACEHOLDER`.
- **The output.** `ASM-TEMPLATE-DIRECTIVE` is written once, as the file's first line, instead of above every unit; every other status line is written as for plain files. Findings, notes and reasons quote placeholders as the template writes them.
- **The report** says `"templates": true`, and each file lists its placeholders, unresolved candidates and directives under `template`.

### Fragments, routine halves and value kinds

Not every template is whole statements. The pack's `[template]` section says what the rest are, so each converts as what it is:

```toml
[template]
# What a placeholder's values are. Default: name.
values = { KEYTYPE = "type", NOTE = "text", LIMIT = "number", FILTER = "expression" }
# Templates that hold part of a statement (first match wins). Default: statements.
fragments = [
  { glob = "where/**", kind = "predicate" },
  { glob = "columns/**", kind = "select-list" },
  { glob = "parts/body*.sql", kind = "routine-body" },
]
# A routine's opening and closing templates, converted as one routine.
pairs = [{ head = "parts/head.sql", foot = "parts/foot.sql" }]
```

- **Fragment kinds** are `statements`, `predicate` (what follows `WHERE`), `expression` (one value, also `select-list`), `set-list` (what follows `UPDATE … SET`) and `routine-body` (statements inside `BEGIN … END`). A fragment is converted inside a stand-in statement of that kind, from T-SQL only, and cut out again with the template's own leading and trailing white space. If converting it changed the stand-in around it (a declaration hoisted, a parameter added, code moved across its edge, or a rule that did not apply), the template is kept as it is and flagged `template.context-leak` (differs), with the conversion's own reason when it gave one: it cannot be converted on its own. Otherwise every unit carries `ASM-TEMPLATE-FRAGMENT`: its names were not bound and its meaning in the woven statement was not checked. The stand-in's table is in the catalogs with unknown columns, so binding against it is never a finding.
- **A routine-body fragment knows no parameters, unless the tree lists them.** Converted on its own, the T-SQL parameter `@Id` in a body reads as a local variable and becomes `v_id`, while the opening template turns the same parameter into `p_id`. The unit then fails binding (differs), and so do the woven instances: nothing is claimed. List the routine's parameters in `template-parameters.toml` (below), or convert such a body by hand, or weave it into its routine before converting.

#### Parameters of the routine a body is woven into

A generator often writes the routine header itself and weaves only the body from a template; the parameters the body uses are declared in that header, not in the template. A file `template-parameters.toml` at the root of the template tree lists them, per template, as T-SQL declarations:

```toml
["procs/update_item.sql"]   # path from the tree root, with / (a \ is read as /)
parameters = ["@mode int", "@item_name varchar(100) output"]
```

- A template with an entry is converted as a `routine-body` unless a `[[template.fragments]]` rule gives its path another kind (then the entry is ignored). A `routine-body` rule without an entry converts as before, with no parameters.
- The body is converted inside `CREATE PROCEDURE … (declarations) AS BEGIN … END`, so its names bind against the list and read as the target's parameters (`@code` becomes `p_code` in PostgreSQL). A name the body uses that the list leaves out is still `bind.unknown-variable`: the list is never completed by guess.
- Each unit still carries `ASM-TEMPLATE-FRAGMENT`, now saying how many parameters were declared: the weave itself is checked only by the instance check.
- Each declaration is one `@name type [OUTPUT]` on one line, with no `;`, comment, top-level comma or unbalanced parenthesis, and each name is listed once (T-SQL names ignore case). A body the stand-in still swallows (no unit comes out of code) is `template.context-leak` (differs), never converted. A file that does not read, or an entry that is not a table with a `parameters` list of such strings, stops the conversion and names the entry.
- Only a source tree (a directory) is read for it; `--template` conversions of a single file have none.
- **Pairs** are converted together, as one routine, with a marker between them, and split again at the marker. If the conversion moved code across the marker, both templates are kept as they are and flagged `template.pair-split` (differs). A template is in at most one pair; the bodies woven between the halves are converted on their own, as fragments.
- **Value kinds**: only `name` values are converted as names (`ASM-TEMPLATE-PLACEHOLDER`, checked against the target's name rules per instance). A `text` or `number` value means the same in every dialect. A `type`, `expression` or `sql` value is dialect code the rules cannot convert, so its unit is a decision (`template.value-per-dialect`): give the target's value in the instance manifest under `params_for`. The instance check discharges that decision, and a dialect-code value given only once, for every dialect, stays an assumption there (`ASM-TEMPLATE-VALUE-SAME`).

A converted template tree is never the last word: a template is right only when every instance the generator weaves from it is, which the instance check verifies.

### Checking every woven instance

```sh
sqldiff instances instances.toml --source templates/ --target out/ --to postgres -o check/ --pack PACK \
    [--woven generated/] [--woven-target generated-pg/] [--accept ASM-…] [--catalog schema.sql] [--since check/]
sqldiff instances instances.toml --generator-only --woven generated/ --woven-target generated-pg/ \
    --to postgres -o check/ [--pack PACK]
```

`sqldiff instances` weaves every instance the generator produces twice, from the source templates and from the converted ones, with the same values, and checks each pair. The manifest lists the instances (a template, or several parts in order), their parameter values, and values per dialect where a value differs between dialects:

```toml
[params]                        # every instance
SCHEMA = "dbo"
[params_for.postgres]           # every instance, PostgreSQL side only
SCHEMA = "public"

[[instance]]
name = "Sales/SaveCustomer"     # unique; also the woven files' name
template = "procs/save-entity.tpl.sql"
output = "Sales/SaveCustomer.sql"   # the generator's own output under --woven (default: name + .sql)
params = { ENTITY = "Customer", TABLE = "Customer" }

[[instance]]
name = "Sales/Composed"
parts = ["header.sql", { template = "body.tpl.sql", params = { X = "1" } }]
```

Values merge manifest, then instance, then part; at each level a dialect's own values win. The names the manifest gives values for are the parameter list for the placeholder rules (`--parameter` adds more). The pack's `[template] include` names the special form that pulls another file in: its first capture is the path, next to the including file first, else from the tree root, never outside it (a symbolic link that points out of the tree is not followed). Any other special form is generator logic the weaver cannot run, and so is a missing value or an include cycle: that instance is **not woven** and nothing about it is claimed.

Each target instance is checked the way `sqldiff convert` checks its output, with the catalog of every woven instance on its side (and any `--catalog`):

| Check | Fails as |
|---|---|
| The target weave parses as the target dialect | differs |
| The output check: binding, leftover source syntax, target limits, hazards | differs |
| The engine's diff of the source weave against the target weave: a proven difference, or source syntax left in the target | differs |
| The engine's diff: a finding it could neither prove nor rule out (`equiv.unproven`, …) | unknown |
| The engine's diff could not compare a statement at all (`equiv.not-covered`): today every DDL statement other than a table below | unknown |
| A `CREATE TABLE` (which the engine does not compare) that is not, token for token, the table the conversion rules write from the source instance's table (`ddl.not-as-converted`); the schema may differ only where both sides use their default (`dbo`, `public`) | unknown |
| The engine's diff: a finding equal only under assumptions (listed with the rule), or an assumption about this pair (`ASM-ARGUMENT-LENGTHS` when a parameter's type differs) | under assumptions |
| A name a value is part of is a PostgreSQL reserved word unquoted (`Order`, `user`), or longer than 128 characters on Db2 for i | differs |
| A PostgreSQL name over 63 bytes is truncated (`ASM-PG-NAME-TRUNCATED`); two values that truncate to the same name | under assumptions; differs |
| A Db2 for i name from a value: no verified reserved-word list is built in (`ASM-DB2I-RESERVED-UNCHECKED`) | under assumptions |
| A `type`, `expression` or `sql` value with no value of its own for the target (`params_for`) (`ASM-TEMPLATE-VALUE-SAME`) | under assumptions |
| Two instances create the same table or routine (the later one fails or replaces the other; binding used one definition) (`weave.object-twice`) | unknown |
| The source weave does not parse | unknown |

The woven instances discharge `ASM-TEMPLATE-PLACEHOLDER`, `ASM-TEMPLATE-DIRECTIVE`, `ASM-TEMPLATE-SHARED-VALUES`, `ASM-TEMPLATE-FRAGMENT` and `template.value-per-dialect`: the values are known, the includes and fragments woven in, and each instance woven with its own values. Name checks apply only to `name` values. The status lines `sqldiff convert` wrote into the converted templates are read from the woven target, and the rule assumptions and decisions on them stand, because no instance can check them: an assumption you know holds is accepted with `--accept ID` (listed in the report); a decision or a difference is resolved by hand and its line deleted.

Tables get the same bar as `sqldiff convert`'s own output: the woven target's tables, in order, must equal what the built-in conversion rules write from the woven source's tables (with default options: the pack and catalogs do not take part, so a table a pack made `convert` write differently comes out unknown), ignoring layout, comments and the letter case of unquoted names, and the rules must convert them (their assumptions are listed, `ASM-DBO-SCHEMA` with the engine's). A table written another faithful way (`int` for `integer`, a constraint in another place) is unknown, never converted: rewrite it as the rules do or check it by hand.

With `--woven DIR` (the generator's real output) each source weave must equal its `output` file, ignoring trailing white space, or the instance is not woven (`weave.generator-mismatch`, with the first line that differs), and every file there that no instance names is listed under "not in manifest". That is what shows the manifest describes the generator completely.

#### Checking what the generator really writes

Behaviour is best guaranteed on the generator's own output, so an instance is **done** only when both of its sides were checked on it; SQLDiff's weave alone is evidence about the templates, not about what the generator writes.

- **The generator weaves the converted templates unchanged.** Give its output for the target with `--woven-target DIR` (same `output` paths as under `--woven`). Each target weave must equal its file there, ignoring trailing white space, or the instance is not woven (`weave.generator-target-mismatch`, with the first line that differs): the generator does something the weaver does not, and nothing is claimed. Files there that no instance names are listed as "not in manifest" too.
- **The generator was changed for the target** (dialect logic, other includes), so its target output is not a weave of the converted templates. Check its output alone with `--generator-only --woven DIR --woven-target DIR`: each instance's source output against its target output, with the same checks as above (the target parses, the output check, the engine's diff, tables as the rules write them, the names the values make). Nothing is woven, so no `--source` or `--target`. Results map back to the templates the manifest names for each instance (a template's status is the worst instance), not to the generator's includes, which it does not know; there is no "not exercised" list. The values' names are found as the name tokens of the target output that hold a `name` value, ignoring letter case; a keyword that holds one is checked too, which can only make an instance worse. A missing or unreadable output on either side leaves the instance not woven.
- **No target output yet.** An instance with no file under `--woven-target` (or no `--woven-target` at all), or no source output under `--woven`, is checked on SQLDiff's weave only: its status is reported as usual, but the report lists the sides in `weave_only`, says "checked on SQLDiff's weave only", and it never counts as done.

The report gives `done` per instance and per template, totals of `done` and `weave_only`, and `complete`: every instance done, every converted template exercised and all generator output accounted for. With `--woven-target` the exit code is 1 when an instance has no target output there.

#### Re-running after an edit

`--since PATH` (a previous `instance-report.json`, or its output directory, which may be `-o` itself with `--overwrite`) checks again only the instances whose own inputs changed: every instance is still woven (that is cheap, and the catalogs need every instance), and an instance reuses the earlier result only when its woven source and target text, its values, its generator output and its name are what they were. Everything else every check reads must be unchanged too, or every instance is checked: the sqldiff build (the executable's hash), the dialects, the mode, `--accept`, the pack's value kinds, the catalogs (`--catalog` and the ones built from all woven instances, so changing a table or a routine's parameters re-checks everything; changing a body does not). The checks across instances (names PostgreSQL truncates to the same name, an object two instances create) are always worked out again over every instance. The earlier report is a cache, not evidence: a result in it is reused as it stands, so a report edited by hand (an item deleted, say) carries the edit into the new run. Give `--since` only a report your own run wrote. The report says how many results were `reused`; apart from that it is the same report a full run writes (tested on the test trees, and over 80 random edits of a tree of 78–84 instances).

This is a stricter bar than `sqldiff convert`'s, where only a proven difference holds a unit back: an instance is converted only when no finding of the diff is left open. The assumptions the diff makes about every pair (name folding, the default schema, T-SQL's ownership chain) are listed per instance as `engine_assumptions` and do not count, as in `convert`; any other assumption the diff makes about the pair (`ASM-ARGUMENT-LENGTHS`, say) counts, unless accepted with `--accept`.

`check/instance-report.json` and `.md` give each instance's status and items (side, line in the woven file, rule), each converted template's status (the worst instance that uses it, includes too) and the converted templates no instance uses ("not exercised", never checked). The woven files are written to `check/source/` and `check/target/`. Exit code 0 when every instance is converted or converted under assumptions and all generator output is accounted for, 1 otherwise.

### Keeping dialect trees in step

Once the generator keeps one template set per dialect, the sets drift: a template is added, changed or rewired in one tree and not in the others. `sqldiff drift` finds that, in CI or before a commit:

```sh
sqldiff drift --tree tsql=templates/mssql --tree postgres=templates/pg --tree db2i=templates/ibmi -o drift/ --pack PACK \
    [--reference tsql] [--base origin/main] [--manifest instances.toml] [--accept ASM-…] [--extension tpl …]
```

| Check | Rule |
|---|---|
| Every template (same relative path) is in every tree | `drift.missing` |
| A template has the same placeholder names in every tree, so one set of values weaves all of them | `drift.placeholders` |
| A template has the same directives (the pack's special forms, with their arguments) in the same order in every tree | `drift.directives` |
| With `--base REV`: a template changed between the merge base of `REV` and `HEAD` and the working tree in some trees and not in all | `drift.changed-alone` |

A change made in one tree on purpose adds the pack's `intentional_difference` author marker to that template (`-- SYNC-OK: why`, say) in the same change; the report lists it with its reason instead of failing. Only a marker on a line the change adds counts: one committed earlier explains no later change. With `--manifest`, every instance is also woven from the reference tree (the first `--tree` unless `--reference` says otherwise) and from each other tree and checked exactly like `sqldiff instances`, each into `drift/instances/<dialect>/`; a hand edit that changes what a template means then fails as differs or unknown there.

`drift/drift-report.json` and `.md` list every finding by template and tree. Exit code 0 when nothing drifted and every instance check passed, 1 otherwise, so a CI step is the command itself:

```yaml
- run: sqldiff drift --tree tsql=templates/mssql --tree postgres=templates/pg --tree db2i=templates/ibmi
         --base origin/${{ github.base_ref }} --manifest instances.toml --pack .sqldiff/pack -o drift/
```

`--base` needs the base branch's history in the checkout (`fetch-depth: 0`).

### Review decisions

What people decide about converted units is kept in `review-decisions.jsonl` at the root of the converted tree, committed with it (`sqldiff_convert::review`). Each line names a unit by its id (a hash of its file path, input text and output text, `~2`, `~3` for repeats), the rule it is about, the state, `by` (`human` or `agent`), the author, a reason, the time, and the SHA-256 of the exact bytes of the whole input and output file it was made on. `by` is whatever the line says, so the CLI, GUI and MCP writers set it themselves and never take it from their caller.

| State | Means | Allowed |
|---|---|---|
| `accepted` | The named assumption holds here | People only; the rule must be an assumption of the unit; a reason |
| `picked` | The target the conversion chose is right | People only; the rule must be a decision of the unit; a reason |
| `approved` | The unit's output is right as written | People only; a reason |
| `rejected` | The unit is wrong; it stays open | People only; a reason |
| `written` | The output was written by hand, not by the rules | People and agents |
| `commented` | A remark | People and agents; discharges nothing |

A decision applies only while both files are unchanged since it was made, to the byte: text around a unit can change what it means, so any change outdates it and someone confirms it again. A decision never changes a unit's status. It can discharge assumptions and decisions; a difference, a refusal or what the engine could not prove is fixed only by changing the output and checking again. A unit is *reviewed* when nothing undischargeable is left, every assumption and decision is accepted or picked, no one's current rejection stands (records are kept per author, so one person's approval never replaces another's rejection), and output an agent wrote is approved by a person. A file is reviewed when every unit is and no gating finding is unplaced. A plainly converted unit nobody approved is not reviewed: it shows as "nothing found", and a reviewed unit as "accepted in review", never as converted. Lines that do not parse or are not allowed (an agent accepting an assumption, a verdict without a reason) are listed and never applied.

`sqldiff convert` and the MCP `convert_tree` tool apply the ledger they find in the output directory. `conversion-report.json` then gives every unit its `id`, the rules of the engine's findings on it (`findings`) and its `review` (reviewed, open assumptions and decisions, what cannot be discharged, who wrote the output, and every decision with whether it still applies and why not); each file its `review` (reviewed, units reviewed and outdated, orphaned records); and the report a `ledger` summary. Plainly converted units are listed under `converted_units` (nothing found, not proven), the rest under `units` as before. Statuses, counts and the exit code are the same with or without a ledger.

### Output written by hand

A `written` record with a `text` replaces a unit's output on every later conversion: the conversion writes the rules' output, then puts the text in place of the unit it names. The record names the unit as the rules wrote it, so it keeps applying while that unit's input and the rules' output for it are unchanged, whatever changes around it; when either changes, the record is orphaned and listed. In a plain file the text replaces the unit's output before the check, so it is checked against the source like the rules' output and can come out differing or not proven. It is never better than the rules' output was: the rules' assumptions and decisions on the unit stay, and the text itself carries `ASM-HAND-WRITTEN`, since the check allows the same dialect mappings it allows the rules (a dropped `dbo` schema, mapped types) and a text written by hand may lean on them without saying so. In a template the check of the template's text does not apply to the text, so it is spliced in after the check and the unit is not proven (`hand-written.unchecked`) until the woven instances are checked by `sqldiff instances`.

A person's text replaces an agent's draft for the same unit, and a newer text by the same author replaces their older one. Two different texts from two people (or only from agents) are a conflict: neither applies, and the unit is marked differs (`review.conflicting-texts`) until one is removed. Output an agent wrote is never reviewed until a person approves it (tier 3 of the queue).

The MCP tool `write_unit` is how an agent drafts a unit: it takes the unit's id from `conversion_queue` or `convert_tree`, records the text as `by: agent` whatever its caller says, converts the tree again, rewrites `out` and the queue, and returns the unit's new id, status, notes and findings. It is refused, and records nothing, when a file in `out` was edited since the last conversion.

Editing a converted file directly is not a review step: the next conversion would overwrite the edit. `conversion-report.json` keeps the SHA-256 of every file it wrote (`output_hash`), and `sqldiff convert --overwrite` refuses to replace a file edited since, naming it, unless `--discard-edits` is given (the MCP `convert_tree` takes `discard_edits`). Record the edit as a `written` text instead, so every later conversion applies and checks it.

### The review queue

`sqldiff convert` also writes `review-queue.json` and `review-queue.md`: what a person should look at, worst first, ranked by tier and never by a score (a score would let many clean units average away one that nothing was claimed about). Units the ledger says are reviewed are not listed; nothing is ever listed as safe.

| Tier | Items |
|---|---|
| 1 | Differs, not converted, rejected in review; source files that could not be read as text; a table, routine or type several units fail to bind on and nothing else is wrong with, as one item (convert or create it first); gating output findings outside any unit; templates whose instances differ |
| 2 | Not proven; templates whose instances are unknown or not woven, or have a status the queue does not know; templates with an instance checked on SQLDiff's weave only, not on the generator's output (whatever its status, and every template of a report that predates the generator check); templates no instance uses; generator source or target output no instance accounts for |
| 3 | Output an agent wrote that no person approved |
| 4 | Open decisions |
| 5 | Open assumptions, unverified vendor facts (`ASM-FACT-*`) and template premises (`ASM-TEMPLATE-*`) first |
| 6 | Only with `--queue-all`: plainly converted units nobody approved (nothing found, not proven) |

Inside a tier, items with the most instances woven from their template come first, then the most units, then path and line. With `--instances PATH` (`instance-report.json` from `sqldiff instances`, or its directory) each template is also judged by its woven instances and listed with the ones that fail. The MCP tool `conversion_queue` converts the tree again in memory, applies the ledger in `out` and returns the same queue; it writes nothing, and no MCP tool records a verdict.

### The done gate

`sqldiff review-status SRC OUT --to TO [--template] [--instances PATH] --require-complete` is the check for CI. It converts SRC again in memory with the ledger in OUT, writes nothing, and exits with 1 unless the review is complete:

- every unit is converted or converted under assumptions: nothing differs, is not converted or is not proven, and no output finding is outside a unit;
- every assumption is accepted and every decision picked by a person, by name;
- no current rejection stands, and every unit an agent wrote is approved by a person;
- no decision was made on other bytes of its file (outdated decisions block until their author confirms them again);
- no ledger line fails to parse or is not allowed (it may be someone's rejection), and every source file could be read;
- OUT holds exactly what converting SRC gives now, so a hand edit or a stale tree fails, and no file with a converted extension that no source file converts to (a source deleted since);
- for templates (`--template`), an instance report is given, is `complete` (every instance converted and checked on the generator's own output on both sides, every template exercised, all generator output accounted for), and was made on these trees: `sqldiff instances` records a hash of its source, target, manifest and generator output trees, and the gate hashes them again (the manifest and generator output at the paths the report names).

A template unit written by hand is not proven by `convert` (`hand-written.unchecked`); it passes only when that complete, current instance check is given, since only the woven instances check it. Plainly converted units need no decision: they are counted as "nothing found", never as reviewed. The gate lists every assumption accepted and decision picked, with the number of units and who. `--json` prints the whole gate.

### Reviewing in the GUI

`sqldiff-gui review SRC OUT --to D` (with `--template --pack P`, `--parameter`, `--extension`, `--no-catalog` and `--instances PATH` as for `sqldiff convert`) opens a page over the converted tree OUT: the review queue by tier on the left, and for the selected item the source and the converted output side by side (the unit highlighted in context), the rules' notes, the engine's findings and, for templates, the instances woven from it that are not converted. A missing object several units fail to bind on shows each of its units; template items, unplaced findings, unexercised templates and generator output outside the manifest explain what to fix instead, since no decision applies to them.

The page's actions append records to `OUT/review-decisions.jsonl` and change nothing else: OUT's converted files are never written. Accept names one assumption of the unit, Pick one decision, Approve and Reject the whole unit (or, for Reject and Comment, optionally one note); each needs a reason, and a comment discharges nothing. Ticking several queue rows offers Accept for an assumption they share, as one record per unit, all or none. The page asks for your name once (remembered in this browser) and the server builds every record itself: `by` is always `human`, a request that names `by` or any other unknown field is refused, and the hashes are those of the input and of the conversion's output as the server has it now. The page sends back the hashes of what it showed, so a decision about a file that changed meanwhile is refused rather than recorded on text nobody saw. A record that would not apply (an accept naming no assumption of the unit, a pick naming no decision) is refused too, and so is an approval while a difference, a refusal or what the engine could not prove is on the unit: an approval never stands in for fixing the output.

After every action the sources are read again, the ledger applied again and the queue rebuilt; the tree is converted again when a source changed, and otherwise the previous conversion is kept, since the same files with the same options convert the same way (`tests/convert_review.rs` checks that the kept report equals a fresh one). A reviewed unit leaves the queue and is listed, folded, as *accepted in review*, with its status unchanged; it is never shown as converted. A plainly converted unit reads *nothing found, not proven* and is listed only with "Nothing found too" (tier 6). Items whose decisions were made on other file contents are marked *outdated*; banners list ledger lines that were not applied, decisions about units that no longer exist, and files in OUT that differ from what this conversion writes (converted with other options, or edited by hand).

- **Navigation:** `Alt+↓` / `Alt+↑` next and previous unit that needs attention, `Alt+Home` / `Alt+End` first and last. The status chips in the header jump to the next unit with that status.

## Rules (P0)

Token-level rules over the lossless CST; expressions are still flat, so nothing here relies on operand types beyond what declarations and literals show.

- Routines: `CREATE PROCEDURE` → `CREATE OR REPLACE PROCEDURE … LANGUAGE plpgsql AS $$ … $$`, scalar functions likewise; parameters `@ItemId` → `p_item_id`, locals → `v_…` (the prefixes avoid PL/pgSQL's variable/column ambiguity); `OUTPUT` → `INOUT`; `RETURN n` in a procedure → an `INOUT return_code`. `DECLARE` is hoisted, with initialisers kept as assignments in place. Scripts with variables or control flow become a `DO` block.
- Control flow: `IF/ELSE IF/ELSE` → `IF/ELSIF/ELSE/END IF`, `WHILE` → `WHILE … LOOP`, `BREAK` → `EXIT`, `TRY/CATCH` → `BEGIN … EXCEPTION WHEN OTHERS` (with the subtransaction assumption), and the `ROLLBACK; THROW;` CATCH idiom → let the error propagate.
- Statements: `SET @x = …` → `:=`, `SELECT @x = … FROM` → a block `DECLARE r record; BEGIN FOR r IN SELECT … LOOP x := r.c; END LOOP; END;` (T-SQL assigns row by row: no row keeps the old value, several rows leave the last; `SELECT … INTO` would set NULL and keep the first), or a plain `SELECT … INTO` when the query always returns one row (an aggregate without `GROUP BY`, `HAVING`, a window, `TOP`, `OFFSET` or `FETCH`), or when the statement reads a variable it assigns anywhere but as a target (in T-SQL that accumulates or filters row by row) or uses a name starting with `sqldiff_` (the loop's own names); those two forms keep `ASM-SELECT-ASSIGN-CARDINALITY`, `TOP n` → `LIMIT n`, `PRINT` → `RAISE NOTICE`, `THROW` → `RAISE`, `EXEC` → `CALL`, `DELETE t` → `DELETE FROM t`, `DELETE t FROM t JOIN u ON c WHERE w` → `DELETE FROM t USING u WHERE (c) AND (w)` (Db2 for i: `DELETE FROM t WHERE EXISTS (SELECT 1 FROM u WHERE (c) AND (w))`), session options that PostgreSQL always behaves like. Transaction statements in a procedure or a script that becomes a `DO` block: a `BEGIN TRAN … COMMIT` that wraps all the durable work (before and after it only declarations, `SET`, `PRINT` and `SELECT` without `INTO`; no other transaction control, `@@TRANCOUNT`, `XACT_STATE`, TRY/CATCH, `THROW`, `RAISERROR`, `EXEC`, `GOTO`, table variables, or a `RETURN` before the end; `SET XACT_ABORT ON` before it or a single writing statement inside) is dropped (`tsql.txn.wrapper`), because the `CALL` or `DO` is one transaction already and inside a caller's transaction both sides leave the work to the caller; the engine shows such a body equal with and without a caller transaction. Any other `BEGIN TRAN` is dropped and `COMMIT`/`ROLLBACK` kept under `ASM-NO-CALLER-TXN` (callers `CALL` in autocommit, which a deployment profile accepts once); inside a caller's transaction T-SQL's inner `COMMIT` only decrements `@@TRANCOUNT` where PostgreSQL refuses it, and the engine reports that difference when the assumption is denied. A procedure or script with `SET XACT_ABORT ON` before its first statement that is not a declaration, `SET`, `PRINT`, `THROW` or `SELECT` without `INTO`, whose statements outside `BEGIN TRAN … COMMIT` T-SQL commits one by one, gets a `COMMIT` after each such writing statement (`tsql.txn.autocommit`, under `ASM-NO-CALLER-TXN`; PostgreSQL allows it inside `IF` and `WHILE` of a procedure `CALL`ed outside a transaction block, and a temporary table survives it), so a later failure leaves the earlier statements durable on both sides. It is refused, and the body left as before, with `SET XACT_ABORT OFF` or no `SET XACT_ABORT ON` (whether T-SQL carries on after an error depends on the error), `EXECUTE AS OWNER` (PostgreSQL refuses `COMMIT` in a `SECURITY DEFINER` procedure), TRY/CATCH, `ROLLBACK`, `SAVE`, `XACT_STATE`, `@@TRANCOUNT`, `RAISERROR`, cursors, `GOTO`, isolation or implicit-transaction settings, nested or unbalanced `BEGIN TRAN`, a `RETURN`/`BREAK`/`CONTINUE` inside a transaction, or fewer than two transactions in all. Statement-level equivalence does not place a `COMMIT` between data statements or inside an `IF` or loop; the engine counts such a placement compared only when the behaviour model lowered the whole routine on both sides (one routine in the artifact) with no imprecise, untested or durability-unknown path and every finding equal or equal under assumptions. It summarizes loops after two iterations, so a `COMMIT` inside a loop is written but stays not proven. Checked on SQL Server 2022 and PostgreSQL 18.
- DDL: types, `IDENTITY` → `GENERATED ALWAYS AS IDENTITY`, `#temp` → `TEMP`, `BIT` defaults, storage options and `CLUSTERED` dropped, views → `CREATE OR REPLACE VIEW`.
- Table variables: `DECLARE @t TABLE (…)` in routine `dbo.p` → `DROP TABLE IF EXISTS pg_temp.tv_p_t; CREATE TEMP TABLE pg_temp.tv_p_t (…)`, so each call starts empty, and every read and write of `@t` uses that name. The name carries the routine (`tv_<routine>_<variable>`, `tv__<variable>` in a script; cut to 63 bytes with a hash) so a called routine with its own `@t` never replaces its caller's table. `ASM-TABLE-VARIABLE`: the table lives for the session, not the batch, so it must not be read after the routine, the routine not re-entered while it is in use, and no transaction rolled back while it holds rows: T-SQL keeps a table variable's rows on ROLLBACK, PostgreSQL empties a temp table. A routine with a ROLLBACK (other than rollback-and-rethrow in CATCH) gets the `pg.table-variable-rollback` decision. Refused: a DECLARE inside IF, WHILE or TRY/CATCH (T-SQL creates it once per routine; in a loop it keeps its rows from pass to pass) and a table variable in a function (it would have to be VOLATILE). The engine pairs the DECLARE with the DROP and CREATE and compares the column lists, and pairs every write to `@t` with the write to the temp table.
- Expressions: `[x]` → `x` (or `"x"`), `dbo.` dropped, `N'…'` → `'…'`, string `+` → `||`, `ISNULL`, `LEN` → `length(rtrim(…))` (`ASM-TSQL-LEN-BMP`), `CHARINDEX` → `strpos` (a needle that may be empty is tested first: CHARINDEX finds `''` nowhere, strpos at 1), `NEWID`, `IIF`, `GETDATE`/`SYSDATETIME`/`GETUTCDATE`, `CAST`/`CONVERT` types, `CONVERT(varchar(n), x, style)` of a date, datetime or datetime2 → `to_char` for styles 20, 120, 23, 102, 111, 112 and 108 (each type and style checked on both engines, eval/builtins/2026-10-29; a date prints only its date part in style 120; a shorter target becomes `CAST(… AS varchar(n))`), `DATEADD` (see below), `DATEPART` → `EXTRACT(…)::int` (seconds `floor(EXTRACT(SECOND …))::int`, since `::int` rounds 59.9 to 60; weekday `EXTRACT(DOW …)::int + 1` under `ASM-TSQL-DATEFIRST-7`), `YEAR/MONTH/DAY`, `CHAR`/`NCHAR` of a literal 1–127 → `chr`, `DB_NAME()` → `current_database()` (`ASM-SAME-DATABASE-NAME`), `DATEDIFF` for day/month/year (boundary counts, as T-SQL defines them), `STRING_AGG … WITHIN GROUP`, `REPLICATE`, `SCOPE_IDENTITY`, `ERROR_MESSAGE`/`ERROR_NUMBER` in handlers, table hints, `DATEFROMPARTS` → `make_date`, `QUOTENAME(x)` → `quote_ident(x)` (`ASM-QUOTENAME-IDENT`: used as an identifier), `RAND()` → `random()` (`ASM-RAND-PER-QUERY`: once per query in T-SQL, per row in PostgreSQL), `NEXT VALUE FOR s` → `nextval('s')`, `0x…` → `'\x…'::bytea` (PostgreSQL 16+ would read `0x…` as an integer; `ASM-HEX-BINARY`), binary `+` → `||` when every operand is a `0x…` constant or a `varbinary` variable (`SET @b += 0x…` too; next to a number T-SQL adds instead, so `+` stays; `ASM-CONCAT-NULL`). The engine compares binary concatenation as such (`concat-bin`); T-SQL's 8000-byte cut-off for two bounded operands stays T-SQL's own.
- Indexes: `CLUSTERED`/`NONCLUSTERED` dropped (`ASM-CLUSTERED` for a clustered one), filegroups, partition schemes and `WITH (…)` dropped wherever they stand, also after a filter (PostgreSQL rejects `WITH` after `WHERE`). A unique index gets `NULLS NOT DISTINCT`, since T-SQL's holds one row with NULL. Every index notes `ASM-INDEX-NAME-SCHEMA` (index names are schema objects on the target, per table in T-SQL) and a filtered one `ASM-TSQL-FILTERED-INDEX-SET-OPTIONS`. Columnstore, XML and spatial indexes are not converted. The engine compares each converted index (`equiv/ddl.rs`, docs/cross-dialect-proofs.md).
- Schemas: `AUTHORIZATION dbo` is dropped (`ASM-SCHEMA-OWNER`: the target has no role or user profile `dbo`, so the user running the script owns the schema); another owner is kept under the same assumption.
- Sequences: `CREATE SEQUENCE` with every bound written out, because T-SQL starts an ascending sequence at the type's minimum (`-2147483648` for `INT`) and PostgreSQL at 1; the cache is left at PostgreSQL's `CACHE 1` (a larger one is per session and hands out values out of order).
- `DATEADD` keeps the type of its date argument, as T-SQL does, so the rewrite depends on that type: from a declared variable or parameter, a column of a table defined in the converted files (a bare name needs every table of the statement known and agreeing on the type; a statement with CTEs is not resolved), a `CAST`/`CONVERT`, a nested `DATEADD` or `GETDATE()`/`SYSDATETIME()`. On a `date`, days and weeks are integer addition (`d + 5`, `d - 5`, `d + 7 * n`) and months, quarters and years are `(d + make_interval(months => n))::date`, because `date + interval` is a timestamp in PostgreSQL. Other types get `+ make_interval(…)`, milliseconds and microseconds `+ n * interval '1 millisecond'`. A number that is not known to be an integer becomes `trunc(n)::integer` (T-SQL truncates toward zero), a bigint `(n)::integer` (out of int range is an error on both). Every rewrite carries `ASM-DATEADD-RANGE` (T-SQL raises an error past 9999, or past the datetime/smalldatetime range; PostgreSQL returns the date), years and quarters `ASM-DATEADD-YEAR-END` and times `ASM-DATEADD-TIME-WRAP` (both not on Microsoft's page). Refused with a reason: an unknown date type, a string date (read under DATEFORMAT), what T-SQL itself rejects (`hour` on a `date`, `day` on a `time`, `mcs`/`ns` on `date`/`datetime`/`smalldatetime`), nanoseconds (100 ns rounding), seconds and milliseconds on `smalldatetime`, milliseconds on `datetime` (1/300 s rounding), fractions finer than the type keeps, days or longer on `datetimeoffset` (timestamptz follows the session time zone), and a string number.
- Metadata: `sp_addextendedproperty` with literal arguments → `COMMENT ON SCHEMA/TABLE/VIEW/PROCEDURE/FUNCTION/COLUMN/INDEX/CONSTRAINT` (`ASM-EXTPROP-COMMENT`: the property name is dropped and there is one comment per object). Db2 for i: schemas, tables, views, routines and columns only, since an index lives in the current schema there.
- Keys: `PRIMARY KEY (a ASC)` and `UNIQUE (a DESC)` lose the sort order, which neither target takes in a key's column list; a dropped `DESC` is noted (`tsql.key-order`: only the key's index is built ascending).
- System-versioned tables (PostgreSQL): `PERIOD FOR SYSTEM_TIME` with `SYSTEM_VERSIONING = ON (HISTORY_TABLE = h)` becomes the table plus a BEFORE row trigger function `t_versioning` (`ASM-TEMPORAL-TRIGGER`). INSERT and UPDATE stamp the period columns with `transaction_timestamp()` in UTC and the end of time at the column's precision (`9999-12-31 23:59:59.999999` for `DATETIME2(7)`); UPDATE and DELETE first copy the old row into `h`, also for an UPDATE that changes nothing and for rows written earlier in the same transaction. The statements SQL Server rejects fail too: an explicit period value on INSERT (the columns default to `-infinity`, which no T-SQL value converts to; `DEFAULT` is allowed, as in T-SQL), a period column in an UPDATE's SET list (`BEFORE UPDATE OF`), `TRUNCATE`, and changing a row that a later transaction already changed (Msg 13535). With the tree's catalog the history table must have the same columns by name and type in the same order (else refused with SQL Server's Msg 13523/13524); when the tree has none the output creates it with `CREATE TABLE h (LIKE t)`, as SQL Server creates it; without a catalog that is `ASM-TEMPORAL-HISTORY`. Not reproduced, and said in the note: direct writes to `h` (SQL Server refuses them), schema changes that would need `h` and the trigger to follow, and an INSERT without a column list that leaves the period columns out. Refused: `HIDDEN` period columns, no `HISTORY_TABLE`, a finite `HISTORY_RETENTION_PERIOD`, `SYSTEM_VERSIONING = OFF` in CREATE TABLE, memory-optimized tables, and queries with `FOR SYSTEM_TIME`. A data load that writes period values turns versioning off and drops the period first, and restores both afterwards; those four ALTER TABLE forms become switching the triggers the converted CREATE TABLE made (`ASM-TEMPORAL-SWITCH`): `SET (SYSTEM_VERSIONING = OFF)` disables `t_versioning` and `t_versioning_truncate`, `DROP PERIOD FOR SYSTEM_TIME` disables `t_period_update`, `ADD PERIOD FOR SYSTEM_TIME (start, end)` enables it again, and `SET (SYSTEM_VERSIONING = ON (HISTORY_TABLE = h …))` enables the versioning triggers. Each needs the tree's catalog to show the table created system-versioned with that period and that history table (else refused: the triggers would write another history or none exist). Not reproduced, and said in the note: SQL Server refuses DROP PERIOD while versioning is on, checks on ADD PERIOD that each row's period starts before it ends and on `SYSTEM_VERSIONING = ON` that the history table matches (with `DATA_CONSISTENCY_CHECK = ON`, its rows too); between OFF and DROP PERIOD, and between ADD PERIOD and ON, SQL Server still stamps the period and refuses explicit values; after DROP PERIOD an INSERT that leaves a period column out fails in SQL Server and stores `-infinity` in PostgreSQL. The engine compares each such ALTER with the PostgreSQL statement in its place: the same table, and exactly the triggers named after it, enabled or disabled as the T-SQL form says. A statement that writes a period column is compared as a plain write under `ASM-TEMPORAL-PERIOD-WRITE` (it runs while the period is dropped: with versioning on both sides refuse it); writes to other generated columns stay not compared. In code that switches a table's versioning or writes its period columns, an INSERT that leaves a period column out is not compared: with the period dropped SQL Server takes the column's default or fails, while PostgreSQL stores `-infinity`. Other ALTER TABLE forms on versioning or periods stay refused. A literal `'9999-12-31 23:59:59.9999999'` (the DATETIME2(7) end of time) is marked as differing (`tsql.end-of-time-literal`): PostgreSQL rounds it up to 10000-01-01, so it no longer matches the current rows' end. The rule was checked by running the same DML on SQL Server 2022 and PostgreSQL 18 (same history rows, same failing statements). The engine pairs the trigger's history INSERT with the T-SQL table's declared history write.
- Casts to an integer (PostgreSQL): T-SQL drops the fraction of a decimal or float (`CAST(1.5 AS int)` is 1, `-1.5` gives -1) where PostgreSQL rounds it (2, -2), so `CAST(x AS int)` and `CONVERT(int, x)` of a decimal or float become `CAST(trunc(x) AS integer)` (also for smallint, bigint and tinyint). Integers and money (which T-SQL rounds too) stay as written. A cast to an integer of a value whose type is not known notes `ASM-CAST-INT-FRACTION`, and a string cast to a number `ASM-CAST-TEXT-NUMBER` (T-SQL turns '' into 0, PostgreSQL rejects it). Stored and assigned values are not rewritten yet; the engine reports those as "differs" (`equiv.cast-rounding`). The probes are in `eval/casts`.
- Date and time literals (Db2 for i): a date or date-and-time literal assigned to a variable (`DECLARE @d datetime2(7) = '20200101'`, `SET @EndOfTime = '99991231 23:59:59.9999999'`) is written in the ISO form of the value T-SQL stores (`'2020-01-01 00:00:00'`, `'9999-12-31 23:59:59.9999999'`): Db2 for i reads neither T-SQL's compact `yyyymmdd` as a date nor `yyyymmdd hh:mm:ss` as a timestamp, so the literal as written failed there at run time. Only for date, datetime2(p), datetime and smalldatetime variables, and only where T-SQL stores the literal exactly (`ASM-TSQL-DATEFORMAT-YMD` for a `yyyy-mm-dd` datetime); that Db2 for i reads the ISO string on assignment as a CAST does is fact V33 (`ASM-FACT-V33`, from the IBM i SQL Reference, not yet checked on a real system). The engine reads these Db2 for i strings in a CAST or an assignment, never in a comparison. On PostgreSQL the literal is kept, except T-SQL's end of time `'9999-12-31 23:59:59.9999999'` (any spelling) assigned to a datetime2(7) variable: PostgreSQL keeps microseconds and would round it to 10000-01-01 00:00:00, so it is written `'9999-12-31 23:59:59.999999'` (Davy, 2026-10-29) under `ASM-END-OF-TIME`: the value is only an open-end sentinel, compared with values converted the same way (such as temporal ValidTo columns), and data moved from SQL Server truncates its seventh digit rather than rounding it. In a conversion check the engine shows that pair equal under the assumption, and datetime2(7) or time(7) against timestamp or time (6 digits) equal under `ASM-FRACTIONAL-SECONDS` (no value depends on the seventh digit), for variables and columns; a diff still reports both as differences. Any other seven-digit literal stays as written (`ASM-LITERAL-FRACTION`, `tsql.end-of-time-literal`).
- Bit and boolean (PostgreSQL): `BIT` becomes `boolean` (the `pg.bit-boolean` decision), and PostgreSQL has no comparison, arithmetic or assignment between boolean and the numbers. Wherever the column, variable or parameter types show a bit meeting a number, the output is rewritten exactly. A comparison or list with 0 and 1 becomes FALSE and TRUE. A number stored in a bit (SET, VALUES, DEFAULT, a variable, RETURN, an EXEC argument, the ISNULL replacement) becomes FALSE for 0 and TRUE for any other literal, and `(v <> 0)` for a numeric value, as T-SQL stores it; a CASE stores each of its results so. A CASE or IIF result of 0 or 1 next to a bit result becomes FALSE or TRUE. A bit in arithmetic, CONCAT or a cast to text gets `::integer`, the 0 or 1 that T-SQL computes with. `CAST(n AS bit)` becomes `(n <> 0)`, `~b` becomes `(NOT b)`, `a ^ b` of two bits becomes `(a <> b)`, and `a & b` and `a | b` of two bits become `(a::integer & b::integer)::boolean`. A statement, IF or WHILE condition, CHECK or filtered index where a bit meets a number with no exact form (`b = 2`, `b = n`, `COALESCE(b, 5)`, a CASE mixing a bit with other numbers) is refused with the reason. The idiom rules (MERGE as an upsert, INSERT with SCOPE_IDENTITY) are not used where a bit variable or a bit column is involved, since they do not rewrite bits. Db2 for i keeps `SMALLINT` (`ASM-BIT-SMALLINT`): stored literals are written as 0 or 1, `'true'`/`'false'` as 1/0, and `~b` as `(1 - b)`. The probes are in `eval/bit-boolean`.
- Parameters may be written `@p AS int`.
- CTEs: a recursive CTE gets `WITH RECURSIVE` (`ASM-CTE-MAXRECURSION`: T-SQL stops past its recursion limit, 100 levels by default, PostgreSQL does not). A WITH list stays in front of INSERT, and of UPDATE and DELETE on a real table; a statement that changes a CTE (INSERT included: T-SQL then changes its base table), UPDATE or DELETE with a FROM clause, and MERGE are refused, and so is a recursive list where a query names a later CTE (RECURSIVE would make that name the CTE, where T-SQL reads the table).

`DELETE … FROM` with joins is converted only when the FROM list merely filters the target: every join is an inner or cross join (or a comma), and the target names exactly one FROM table, by its alias or by the one-part name of an unaliased table. Then T-SQL deletes each target row for which at least one combination of the other tables meets all ON and WHERE conditions, once however many match, and that is what `USING` and `EXISTS` do. Outer joins (other than the `LEFT JOIN … IS NULL` idiom), `APPLY`, join hints, nested `ON`, `OPTION (…)`, a target that is no FROM table (`DELETE FROM t FROM u …`) and a target that would bind by a schema-qualified or base-table name to an aliased table (`DELETE FROM dbo.t FROM dbo.t AS x …`) stay not converted. On Db2 for i the conditions move into the `EXISTS` subquery, where an unqualified column resolves to the inner tables first, while T-SQL rejects a column that two FROM tables have (Msg 209); so there every unqualified column must belong to exactly one table by the source catalog (without one, it must be qualified), and conditions with a subquery are refused. The engine's equivalence lowering knows the same semi-join shape on all three dialects, so it checks these rewrites itself rather than reporting them as unsupported. `DELETE TOP (n)` (which rows is unspecified) and `OUTPUT` stay not converted.

`UPDATE x SET … FROM <tables>` with joins (PostgreSQL only) becomes `UPDATE t [AS] x SET … FROM <other tables> WHERE …`: PostgreSQL must not repeat the target in `FROM`, so the target leaves the list and the `ON` condition of the inner join that tied it to its neighbour moves to `WHERE`, next to the original `WHERE` (`UPDATE o SET total = i.qty * i.price FROM orders o JOIN items i ON i.id = o.id LEFT JOIN extra e ON e.id = i.id WHERE w` → `UPDATE orders o SET total = i.qty * i.price FROM items i LEFT JOIN extra e ON e.id = i.id WHERE (i.id = o.id) AND (w)`). That keeps the rows because `(t ⋈ s) ⟕ u` is `t ⋈ (s ⟕ u)` when the `LEFT JOIN`'s condition does not name `t`. So the target must head a comma item or a join chain, or follow its head through an inner or cross join; it must bind like the `DELETE` target above (alias, or one-part name of an unaliased table); a `SET` column may be qualified only by the target; and no other join condition may name the target, by its alias or by an unqualified column the target has (PostgreSQL rejects such a reference, and a `LEFT JOIN` condition cannot move). When a target row meets several rows, T-SQL and PostgreSQL each pick one unpredictably, so the statement is converted only when the source catalog shows at most one: walking out from the target, every other table must have a primary key, `UNIQUE` constraint or unfiltered unique index whose columns are all fixed by equalities to columns of tables already settled, variables or literals (a `LEFT JOIN` table by its own `ON` condition, an inner-joined one by `WHERE` and any inner `ON` condition). `RIGHT`/`FULL` joins, `APPLY`, hints, `OPTION (…)` and `TOP` stay not converted, and so does every `UPDATE … FROM` for Db2 for i. The engine lowers both spellings to one form and proves the uniqueness again from its own catalog, so the rewrite is compared, not trusted; a string key still differs by collation (T-SQL compares it case-insensitively), which the engine reports.

T-SQL `AFTER`/`FOR` DML triggers (PostgreSQL only) become statement triggers: `CREATE TRIGGER s.t ON tbl AFTER UPDATE AS body` becomes `CREATE OR REPLACE FUNCTION s.t() RETURNS trigger LANGUAGE plpgsql AS $$ BEGIN body RETURN NULL; END; $$;` and `CREATE OR REPLACE TRIGGER t AFTER UPDATE ON tbl REFERENCING NEW TABLE AS inserted OLD TABLE AS deleted FOR EACH STATEMENT EXECUTE FUNCTION s.t();`, so the body keeps reading `inserted` and `deleted`. PostgreSQL allows transition tables only on a trigger with one event, so `FOR INSERT, UPDATE, DELETE` becomes one function and one trigger per event, named with `_insert`, `_update`, `_delete` (`pg.trigger-per-event`); and only the images an event has can be declared (`NEW TABLE` for INSERT and UPDATE, `OLD TABLE` for UPDATE and DELETE). The image T-SQL gives empty (`deleted` in an INSERT trigger, `inserted` in a DELETE trigger) becomes `(SELECT * FROM tbl WHERE false)`, aliased as the image when it had no alias. A bare `RETURN` becomes `RETURN NULL`. `IF @@ROWCOUNT = 0 RETURN` (or `< 1`, or with `BEGIN RETURN END`) becomes `IF NOT EXISTS (SELECT 1 FROM inserted|deleted) THEN RETURN NULL; END IF;`, only as the body's first statement: anything before it, `SET NOCOUNT ON` included, resets `@@ROWCOUNT` to 0, and the guard then always returns (`ASM-TRIGGER-ROWCOUNT`: a MERGE fires T-SQL's trigger with its total row count and an empty image). Notes on every trigger: an error in a T-SQL trigger ends the batch and dooms the transaction, in PostgreSQL it fails the statement (`ASM-TRIGGER-ERROR`; the engine runs a T-SQL trigger body as `XACT_ABORT ON`); firing order of several triggers (`ASM-TRIGGER-ORDER`); `ALTER TRIGGER` leaves PostgreSQL triggers for events it dropped (`ASM-TRIGGER-REPLACE`). Not converted, as a whole trigger when any statement is: `INSTEAD OF`, DDL triggers, `WITH EXECUTE AS`, `UPDATE(col)`, `COLUMNS_UPDATED()`, `TRIGGER_NESTLEVEL()`, `EVENTDATA()`, `@@NESTLEVEL`, transaction control (`ROLLBACK`, `COMMIT`, `SAVE`), and every trigger for Db2 for i. The engine compares each event's function with the T-SQL body for that event: `inserted` and `deleted` are known as copies of the table (same columns and keys, but other relations than the table), the image the event lacks is an empty relation of the table on both sides, the guard must be on both sides or neither, and the function must end with `RETURN NULL` (falling off its end is an error in PostgreSQL). Side B must hold exactly one `AFTER` event `FOR EACH STATEMENT` trigger per T-SQL event, on the same table, declaring exactly the event's transition tables as `inserted`/`deleted`, each running its own `RETURNS trigger LANGUAGE plpgsql` function without arguments; anything else leaves the trigger not compared. Writes are paired function by function. A trigger that updates its own table is fired again by PostgreSQL, also for an UPDATE that changes no rows, where T-SQL with `RECURSIVE_TRIGGERS OFF` does not; the engine proves that harmless (`ASM-TRIGGER-REENTRY-OTHERS`) when the only writes to the table are UPDATEs and the UPDATE trigger's function starts with the guard and holds only UPDATEs of the table that each require a column no write assigns to differ between `inserted` and its own `deleted` row (`i.c <> d.c`, `deleted` matched to `inserted` on a whole key no write assigns; these columns must be stored, not computed or generated, on both sides): fired by such a write, every UPDATE matches no row and the next firing returns at the guard. The assumption also covers BEFORE triggers that would change the tested columns. Otherwise, for an INSERT, DELETE or MERGE of the table by a trigger for that event, and for any call in the trigger (the callee may write the table), the trigger is not proven. Checked on SQL Server 2022 and PostgreSQL 18.

`TOP` becomes the target's row limit (`LIMIT n` on PostgreSQL, `FETCH FIRST n ROWS ONLY` on Db2 for i) at every query level: the statement's own query, a view, a subquery (`IN`, `EXISTS`, scalar), a derived table, a CTE and `INSERT … SELECT`, each limit after that query's own `ORDER BY` (`crates/sqldiff-convert/src/tsql/paging.rs`, tests in `tests/top.rs`). Checked on SQL Server 2022 and PostgreSQL 18.6: T-SQL sorts NULL lowest and PostgreSQL highest, so every `ORDER BY` key (also in `OVER (…)`) gets `NULLS FIRST` (ascending) or `NULLS LAST` (descending) unless the tree's catalog declares it a `NOT NULL` column of a table no outer join can leave out; a select-list alias of the same name, a position or an expression always gets it. The engine compares the result: an `ORDER BY` that is not unique carries `ASM-ORDER-TOTAL`, a `TOP` without `ORDER BY` `ASM-PAGE-UNORDERED` (which rows each engine keeps is its own choice; only a review of the statement can accept that), and a count that is not a literal `ASM-PAGE-COUNT-NOT-NULL` (`TOP (NULL)` is Msg 1014, `LIMIT NULL` returns every row). A count must be an integer (an integer literal, or integer variables and literals joined by arithmetic; Db2 for i takes a literal or one variable): T-SQL rejects `TOP (2.5)` and a decimal or string count (Msg 1060) where PostgreSQL rounds. `TOP 100 PERCENT` keeps every row and is dropped (a view keeps its `ORDER BY`, which orders the view's rows on neither side). Not converted, with the reason: `TOP n PERCENT` (ceil(n%) of the rows; no percentage limit on the targets), `WITH TIES` (PostgreSQL ties by its own collation, Db2 for i has none), `TOP` with `OFFSET` (Msg 10741), `TOP` in one query of a `UNION`/`EXCEPT`/`INTERSECT`, and `INSERT`/`UPDATE`/`DELETE TOP (n)`, which change rows SQL Server picks. On Db2 for i, `ORDER BY` and `FETCH FIRST` below the outer query rely on fact V32 (`ASM-FACT-V32`) and `NULLS FIRST`/`NULLS LAST` on fact V19 (`ASM-FACT-V19`), both probed in `probes/db2i` and not yet checked on a real system.

The tests in `crates/sqldiff-convert/tests/convert.rs` convert every T-SQL file in the corpus and require that the output parses as PostgreSQL and carries no T-SQL residue outside commented-out units.

## Db2 for i

`sqldiff-gui convert --to db2i` (or `convert(text, Tsql, Db2i)`) converts T-SQL to Db2 for i SQL PL with the same walk as PostgreSQL: the statements, refusals and engine check are shared, and the target decides the spelling and the notes. The output is diffed against the input by the engine (whose Db2 lowering does not use these rules) and must parse as Db2 for i.

Vendor facts come from [vendor-facts-verification.md](vendor-facts-verification.md). Facts that were never checked on a real IBM i (V4, V9, V15, part of V14) never decide a conversion silently: every unit that depends on one carries an assumption naming the fact (`ASM-FACT-V9`, `ASM-FACT-V14`, `ASM-DB2-SCRIPT-COMMIT` for V4/V5) or the lock-hint note points at V15.

What differs from the PostgreSQL output:

- **Commit level.** Procedures get `SET OPTION COMMIT = *CS` (`ASM-DB2-COMMIT-CS`): each statement is atomic and reads see committed rows, as in T-SQL. Without it the level comes from the creating job (V5), and under `*NONE` nothing is rolled back, not even a failed statement or an ATOMIC MERGE (V2, V4). Scripts run at the job's level, so their transaction statements, `SAVEPOINT` and MERGE note it.
- **Authority.** Every routine states `USRPRF` and `DYNUSRPRF`: `*OWNER` for `EXECUTE AS OWNER` (`ASM-OWNER-PRIVILEGES`), else `*USER`, so the authority never depends on the naming convention at creation (`*NAMING`, fact V25). On PostgreSQL, `EXECUTE AS OWNER` becomes `SECURITY DEFINER`, except in a procedure that commits or rolls back, which PostgreSQL forbids (needs a decision). `RECOMPILE`, `ENCRYPTION` and `SCHEMABINDING` are dropped as having no effect; other `WITH` options need a decision. See [cross-dialect-proofs.md](cross-dialect-proofs.md).
- **Routines.** `CREATE OR REPLACE PROCEDURE … (IN p_x …, INOUT p_y …) LANGUAGE SQL … BEGIN … END;`; declarations are hoisted to the top of the block (variables, then cursors, then handlers, as Db2 requires). `RETURN n` stays (`ASM-RETURN-STATUS`: callers read `DB2_RETURN_STATUS`). Scripts with variables become a compound statement `BEGIN … END;`.
- **Result sets.** A query that returns rows from a procedure becomes `DECLARE result_n INSENSITIVE CURSOR WITH RETURN TO CLIENT FOR …` plus `OPEN result_n;` where it stood, and the procedure declares `DYNAMIC RESULT SETS n`. Functions and scripts still cannot return rows.
- **Control flow.** `ELSEIF`, `WHILE … DO … END WHILE`, with a label on every loop so `BREAK`/`CONTINUE` become `LEAVE`/`ITERATE label`. A statement list left without a statement (a dropped `PRINT`) gets `BEGIN END;`.
- **Errors.** `SET XACT_ABORT ON` (before any other work) becomes an EXIT handler `ROLLBACK; RESIGNAL;` for the whole routine. `TRY/CATCH` becomes a compound statement whose EXIT handler is the CATCH part: unlike PostgreSQL nothing the TRY part completed is undone, which is T-SQL's behaviour. `ERROR_MESSAGE()`/`ERROR_NUMBER()` read variables filled by `GET DIAGNOSTICS` at the start of the handler. The `ROLLBACK; THROW;` idiom becomes `ROLLBACK; RESIGNAL;`. `THROW n, msg, s` → `SIGNAL SQLSTATE '75000' SET MESSAGE_TEXT = msg`; `PRINT` is dropped (needs a decision).
- **Transactions.** `BEGIN TRAN` is dropped (a unit of work is always open under commitment control); `COMMIT`/`ROLLBACK` stay, also inside TRY and CATCH. `SAVE TRAN x` → `SAVEPOINT x ON ROLLBACK RETAIN CURSORS` and `ROLLBACK TRAN x` → `ROLLBACK TO SAVEPOINT x` (V14). A `ROLLBACK TRAN name` that names no savepoint is refused for both targets.
- **MERGE** is kept (`MERGE INTO`, `WHEN NOT MATCHED BY TARGET` → `WHEN NOT MATCHED`); `NOT MATCHED BY SOURCE` (V1) and `OUTPUT` are refused.
- **Temporary data.** `#t` → `DECLARE GLOBAL TEMPORARY TABLE SESSION.t … ON COMMIT PRESERVE ROWS LOGGED WITH REPLACE`; a table variable `@t` in routine `p` → `SESSION.tv_p_t … NOT LOGGED ON ROLLBACK PRESERVE ROWS`, the only form that keeps its rows on rollback (V16); named as for PostgreSQL, refused in the same places, under `ASM-TABLE-VARIABLE`.
- **Queries.** `TOP n` → `FETCH FIRST n ROWS ONLY`, also inside a query (see TOP above); a `SELECT` without `FROM` gets `FROM SYSIBM.SYSDUMMY1`, in views and CTEs too, and the output check flags any that is left (`residue.db2i.select-without-from`); `SELECT @a = … FROM` → `SELECT … INTO` (Db2 raises 21000 on several rows); a table-valued function in FROM, `dbo.f(1) x`, becomes `TABLE(f(1)) x`, the form IBM i documents for a table function reference, with `AS f` added when T-SQL had no alias. T-SQL's own table built-ins (`STRING_SPLIT`, `OPENJSON`, …) and `sys` functions are not converted, and the output check flags any bare call in FROM (`bind.table-function-form`). A data change statement with a WITH list (`WITH c AS (…) DELETE c FROM c JOIN …`) is refused: whether Db2 for i takes a WITH list there was not checked.
- **DDL.** Types map to Db2 (`BIT` → `SMALLINT`, `MONEY` → `DECIMAL(19, 4)`, `DATETIME2(n)` → `TIMESTAMP(n)`, `UNIQUEIDENTIFIER` → `CHAR(36)`, `(N)VARCHAR(MAX)` → `CLOB`/`NCLOB` as a decision, `DATETIMEOFFSET` refused). Column defaults must be constants or `CURRENT TIMESTAMP`, so `DEFAULT NEWID()` or `SYSUTCDATETIME()` is refused. Primary key columns get `NOT NULL`. Several `ADD COLUMN`s are written without commas.
- **System-versioned tables** are refused: Db2 for i has system-period temporal tables (`ROW BEGIN`/`ROW END`, `ADD VERSIONING`), but which clock their values read, their precision and how the history table's columns must match are not verified on IBM i yet.
- **Sequences.** As for PostgreSQL, every bound written out, with `NO CACHE` so values are handed out in order. `NEXT VALUE FOR` is kept (Db2 for i has it). Db2 for i takes no `NEXT VALUE` in a column default, so a T-SQL `DEFAULT (NEXT VALUE FOR s)` on a NOT NULL column becomes a `NO CASCADE BEFORE INSERT … FOR EACH ROW MODE DB2SQL WHEN (N.c IS NULL) SET N.c = NEXT VALUE FOR s` trigger named `<table>_<column>_NEXT` in the table's schema, and the default (with its constraint name) goes (`ASM-SEQUENCE-DEFAULT-TRIGGER`: an INSERT writing NULL into the column fails in T-SQL and gets the next value here; `ASM-FACT-V34`: the trigger fills a column the INSERT leaves out before the NOT NULL check, per row, for MERGE too, probes `V34-*`). On a nullable column (where the trigger could not tell a written NULL from a left-out column) and in a temporary table it is still refused.
- **Built-ins.** `QUOTENAME(x)` → `'"' || REPLACE(x, '"', '""') || '"'` (`ASM-QUOTENAME-IDENT`), `RAND()` stays (`ASM-RAND-PER-QUERY`), `0x…` → `BX'…'` (`ASM-HEX-BINARY`), binary `+` → `||` as for PostgreSQL. `GETDATE()` → `CURRENT TIMESTAMP` (per statement, V20), `GETUTCDATE()` → `CURRENT TIMESTAMP - CURRENT TIMEZONE`, `NEWID()` → `GENERATE_UUID()` (upper case, V13), `LEN` → `LENGTH(RTRIM(…))`, `CHARINDEX` → `LOCATE`, `SCOPE_IDENTITY()` → `IDENTITY_VAL_LOCAL()`, `STRING_AGG` → `LISTAGG`, `DATEADD` → labelled durations (`d + 5 DAYS`, `d - 5 DAYS`, quarters `(3 * n) MONTHS`, weeks `(7 * n) DAYS`, milliseconds `(CAST(n AS BIGINT) * 1000) MICROSECONDS`) with the same type rules and refusals as for PostgreSQL, plus fractions of a second on `time` (Db2 TIME has none) and every `datetimeoffset`; a number not known to be an integer becomes `CAST(n AS INTEGER)`. Month-end clamping (`ASM-DB2-MONTH-END`), time wrap-around (`ASM-DB2-TIME-WRAP`), the cast's truncation (`ASM-DB2-DATEADD-NUMBER`) and the 0001–9999 range error (`ASM-DATEADD-RANGE`) are fact V27, probed in `probes/db2i`, `DATEPART` → `YEAR()`…`SECOND()`, `DATEDIFF` day/month/year → `DAYS(b) - DAYS(a)` and year/month arithmetic. A cast to a number notes V9 unless the operand is a number.

The engine still reports what the rules cannot change: a T-SQL procedure without `XACT_ABORT ON` goes on after a failed statement while Db2 stops (`equiv.error-continues`), and the time source and case sensitivity findings land on their units. `tests/convert_db2.rs` converts the whole T-SQL corpus to Db2 for i and requires that it parses and leaves no T-SQL residue.

## Next (P1 and later)

Expression trees (from the equivalence work) and binding let rules see types, so `+`, comparisons and `ISNULL` stop needing assumptions; the behavioural IR (WP3) and more idiom rules bring `@@ERROR`/`@@ROWCOUNT` checks and transaction structure into scope, and a catalog (`Facts`) lets the idiom rules prove key uniqueness and identity columns instead of assuming them. For Db2 for i, the unverified vendor facts (V4, V9, V15) need a real IBM i before their assumptions can be dropped, and the idiom rules have no Db2 forms yet (MERGE and upserts are converted by the token rules instead).
